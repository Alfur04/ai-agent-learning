# 第 1 周复盘：从零写一个对话机器人

## 这周做了什么

1. 初步写了一个对话机器人
2. 给机器人加入了记忆
3. 加了流式输出功能
4. 加入了历史裁剪

## 学到的东西

1. **大模型本身是无记忆的**——它每次回答只看你这次发过去的 messages，所谓"记忆"是程序把历史存下来、每轮重新发一遍。
2. **流式输出的本质是迭代器**——`stream=True` 后返回的不是完整答案，而是一个可以逐块取的对象；每块只带"新增的字"（`delta`）。
3. **Git 的三个区域**——工作区（改过的文件）→ 暂存区（`add` 之后）→ 仓库（`commit` 之后）。`add` 和 `commit` 分两步，是为了让你挑选"这次提交哪些改动"。
4. **Python 里"空"就是"假"**——`""`、`[]`、`None`、`0` 在 `if` 里都等于 `False`，所以 `if not user_input` 能判断空输入。

## 踩过的坑

### 坑：`.gitignore` 写了却不管用

- **现象**：`git status` 里 `.env` 依然出现在未跟踪列表。
- **原因**：粘贴时每行前面多了两个空格。`.gitignore` 的前导空格是模式的一部分，等于在找名为 `"␣␣.env"` 的文件。
- **教训**：配置文件粘贴后要检查行首；用 `git check-ignore -v 文件` 验证，而不是靠 `git status` 判断。

### 坑：README 代码块没闭合

- **现象**：标题不渲染。
- **原因**：代码块要以三个反引号开始、以三个反引号结束。缺了闭合标记，后面的内容全被当成代码块。
- **教训**：熟悉 Markdown 语法；每段代码块检查首尾是否成对（总数必须是偶数）。

### 坑：`messages` 写在循环里

- **现象**：每轮失忆。
- **原因**：每轮执行 `messages = [...]` 都会新建一个列表并让变量指向它，上一个列表因无人引用被回收。
- **教训**：跨轮累积的数据要放在循环外面，需要每次重置的写在循环里面。

### 坑：`messages[0] + messages[-N:]` 报 TypeError

- **现象**：加历史裁剪时写了 `messages = messages[0] + messages[-20:]`，直接报错。
- **原因**：`messages[0]` 取出的是列表里的第一个元素，也就是一条消息字典。`+` 只能拼接两个同类型的序列，"字典 + 列表"没有定义。
- **解决**：用方括号把元素包成列表——`[messages[0]] + messages[-N:]`。
- **教训**：
  - `x` 和 `[x]` 是两种东西：前者是元素本身，后者是"只装了一个元素的列表"。
  - 看到 `unsupported operand type(s) for +`，第一反应是用 `type()` 分别打印两边，确认实际类型再改。

### 坑：历史裁剪后，消息以 `assistant` 开头

- **现象**：裁剪逻辑写对了，但用脚本模拟多轮后发现，从**第 11 轮开始**，裁剪后的历史第一条非 `system` 消息变成了 `assistant`。
- **原因**：裁剪放在了"追加用户消息之后、调用接口之前"。此时非 `system` 消息是**奇数条**（成对的问答 + 一条新提问），取末尾偶数长度，落点必然错位，从一个 `assistant` 开始。
- **解决**：把裁剪移到"追加助手回复之后"。此时消息严格成对，取偶数长度的尾部，正好从 `user` 开始。
- **教训**：
  - 对成对数据做切片，必须考虑**奇偶性**。
  - 这个 bug **不报错**，接口照样返回结果，只是对话结构变得不规范——真实项目里有大量这类"不崩但逻辑已经错了"的问题。
  - 写完不要只跑两轮就收工，**用脚本模拟几十轮验证**——这个 bug 到第 11 轮才暴露。
